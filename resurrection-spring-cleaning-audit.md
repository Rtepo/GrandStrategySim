## PART 1: Architecture, Dead Code & Duplication

### 1.1 Duplicate Production-Method Registries

**Finding: Two parallel registries with incompatible key schemes.**

| File | Lines | Key scheme | Populated by | Used by |
|------|-------|------------|--------------|---------|
| `registries/production_methods.rs` | 1,471 | Polish display names (`"Baza Wojskowa"`, `"Sąd"`, `"Szpital"`) | `state_building_methods()` + `industrial_production_methods()` | `economy/production.rs:60` — looks up by `building.name` |
| `registries/production_methods_data.rs` | 1,285 | English snake_case (`"mining"`, `"heavy_industry"`, `"energy"`) | `default_production_methods()` | `engine/generator/corporate.rs:760` — looks up by `sector_json_name(sector)` |

Both are merged into `Registries.production_methods` (a single `HashMap<String, BuildingMethods>`) in `registries/mod.rs:72-95`. Because they use disjoint key sets, they coexist without collision — but the result is that **the same `HashMap` is queried by two different code paths using two different key conventions**.

**Consequences:**
- `production.rs` (the per-building production cycle) can only find methods for buildings whose `name` matches a Polish key. Buildings generated by the corporate generator (which uses English sector names) will NOT be found by `production.rs` — it falls through to a hardcoded 1880 fallback method.
- The corporate generator (`best_registry_method`) can only find methods for sectors whose JSON name matches an English key. State buildings (Polish names) will NOT be found.
- There is no single source of truth for "what methods does sector X have."

**Refactoring Blueprint:**
1. Pick ONE key scheme. Recommendation: **English snake_case sector keys** (already used by `Sector` enum's `serde(rename_all = "snake_case")`).
2. Migrate all Polish-keyed entries in `production_methods.rs` to their sector's English key. State buildings (military, police, courts) map to `Sector::PublicAdministration` or a new `Sector::StateSecurity` variant.
3. For buildings that need building-specific methods (e.g., monastery wine vs. scriptorium), add a `building_subtype: Option<String>` field to `Building` and key methods as `"{sector}/{subtype}"`.
4. Delete `production_methods_data.rs` after merging its contents into `production_methods.rs` (or vice versa — keep the file with the larger data set).
5. Update `production.rs:60` to look up by `sector_json_name(building.sector)` instead of `building.name`.
6. Add a test that asserts every `Sector` variant has at least one `BuildingMethods` entry.

### 1.3 Dual Systems (Architectural Duplication)

#### 1.3a Dual Market Systems

The engine runs **two parallel market systems** every turn:

1. **`MarketOrders`** (`economy/market.rs`) — aggregate buy/sell tallies per commodity. Populated by `process_building_cycle_with_geology` (turn.rs:365). Used by `resolve_market_prices` (turn.rs:379) for price discovery and `build_market_signal`. This is the **Target 2/3 price-discovery** system.

2. **`OrderBook`** (`economy/order_book.rs`) — detailed bid/ask order book with per-company orders. Populated by `submit_company_b2b_orders` (turn.rs:474+). Used by `match_orders_with_embargoes` (turn.rs:635) for actual trade execution. This is the **Phase 1+ trade-execution** system.

Both run sequentially: `MarketOrders` discovers prices, then `OrderBook` executes trades at those prices. The two systems never reconcile — `MarketOrders` tallies supply/demand that may not match the actual `OrderBook` bids/asks.

#### 1.3b Dual Production Paths

1. **`process_building_cycle_with_geology`** (`economy/production.rs`) — tallies input demand and output supply into `MarketOrders`. Does NOT touch `building.inventory`. This is the price-discovery production path.

2. **`execute_production_cycle`** (`economy/b2b_orders.rs`) — actually produces goods into `building.inventory`, consumes inputs from inventory, handles overflow/warehouse routing/perishing. This is the physical-production path.

Both run every turn (lines 365 and 1087/1139). The first declares supply/demand for price discovery; the second actually produces. This is intentional but confusing — the declared supply/demand may not match actual production (which is gated by input availability and fulfillment ratios).

#### 1.3c Dual Cash Ledgers on Company

The `Company` struct has **two disconnected cash systems**:

1. **Corporate accounting cash:** `liquid_capital` — used by `process_company` (manager.rs) for profits, overhead, interest, CIT, dividends, expansion. Profit is added from `building.last_profit` (computed in production.rs).

2. **B2B trade cash:** `available_cash` / `debit_cash` / `credit_cash` / `brokerage_account.cash` — used by `b2b_orders.rs`, `order_book.rs`, `transfer_settler.rs` for trade settlement.

**These two systems never reconcile.** B2B trade revenue (credited to `available_cash`/`brokerage_account.cash`) does NOT flow into `liquid_capital`. Corporate profit (added to `liquid_capital`) does NOT flow into `available_cash`. A company can be rich in `liquid_capital` but unable to place B2B bids (no `available_cash`), or vice versa.

**Refactoring Blueprint:**
1. Unify the cash systems: `liquid_capital` should BE `available_cash + brokerage_account.cash` (a computed property, not a separate stored field).
2. OR: add a reconciliation step at the end of each turn that syncs `liquid_capital` to the sum of all cash accounts.
3. Long-term: collapse `available_cash`/`debit_cash`/`credit_cash` into a single `cash` field with an `encumbered` sub-field, and make `liquid_capital` a computed `cash + receivables - payables`.

## PART 2: Financial & Product Black Holes

### 2.1 The Three Critical Money-Creation Black Holes

#### BLACK HOLE #1: Broken B2B Bid Refund Pipeline (MONEY DESTROYED)

**Severity: CRITICAL — permanently destroys encumbered cash every turn.**

**Root cause:** `task.order_book` is reset to empty **BEFORE** the refund functions are called.

In `engine/turn.rs`:
- **Line 624-630:** Per-country `task.order_book.bids` and `.asks` are merged into `global_order_book`, then `task.order_book = OrderBook::default()` (reset to empty).
- **Line 635:** `match_orders_with_embargoes(&mut global_order_book, ...)` matches trades. Unfilled bids remain in `global_order_book.bids`.
- **Line 636:** `all_trades = global_order_book.trades.clone()` — only trades are extracted. `global_order_book` is never used again.
- **Lines 757-776:** `refund_unfilled_bids(&task.order_book, ...)` is called — but `task.order_book` is EMPTY (reset at line 630). The refund does nothing.

**Second bug:** Even if the order book weren't empty, the WRONG refund function is called. `order_book::refund_unfilled_bids` (line 415) credits `company.liquid_capital` — but the encumbrance was on `debit_cash`/`available_cash`. The correct function is `b2b_orders::refund_unfilled_bids` (line 642, exported as `refund_unfilled_b2b_bids`), which properly does `debit_cash -= refund; available_cash += refund`. But this correct function is **never called from the turn loop**.

**Impact:** Every turn, companies encumber cash for B2B bids (`available_cash -= encumbrance; debit_cash += encumbrance`). Filled bids are settled (releasing `debit_cash`). But unfilled bids' encumbrance is NEVER released. `debit_cash` grows monotonically. The encumbered cash is permanently trapped — effectively destroyed.

**Fix:**
1. After `match_orders_with_embargoes`, redistribute `global_order_book.bids` back to per-country order books (by matching `buyer_id` to country's companies).
2. Call `b2b_orders::refund_unfilled_bids` (the correct one) on the repopulated per-country order books.
3. Delete `order_book::refund_unfilled_bids` (the wrong one) or rename it to avoid confusion.
4. Add a test: after a turn with partial fills, assert `sum(debit_cash) == sum(filled_trade_values)`.

#### BLACK HOLE #2: Phantom Loan Repayments (MONEY CREATED FROM NOTHING)

**Severity: CRITICAL — creates bank reserves from thin air every turn.**

In `state/banking.rs:1995-2032` (the loan repayment loop inside `process_banking_turn`):

```rust
for bank in companies.iter_mut() {  // iterates ONLY banks
    for loan in &mut bs.loans_issued {
        let interest = loan.outstanding_balance * loan.interest_rate;
        loan.outstanding_balance += interest;
        let payment = loan.principal / loan.term_turns as f64 + interest;
        let actual_payment = payment.min(loan.outstanding_balance);
        loan.outstanding_balance -= actual_payment;    // ✓ bank's loan asset decreases
        repaid_total += actual_payment;
    }
    bs.reserves_at_central_bank += repaid_total;       // ✓ bank's reserves increase
}
// ❌ The BORROWER's available_cash is NEVER debited!
```

The doc comment (line 1867) claims "borrowers repay from `available_cash`" and "borrower `available_cash` decreases" — but the code only iterates `for bank in companies.iter_mut()`. The borrower (a non-bank company) is never touched. The bank's reserves increase by `repaid_total` but no company's cash decreases by the same amount.

**Impact:** Every turn, bank reserves increase by the total principal+interest repaid, but no borrower pays anything. This is pure money creation. Over 100 turns, this compounds into the 109,154% capital drift seen in the simulation telemetry.

**Fix:**
1. The `Loan` struct needs a `borrower_id: String` field (currently missing — see `state/banking.rs:144`).
2. After computing `actual_payment` for each loan, find the borrower company and debit its `available_cash` (or `brokerage_account.cash`) via `transfer_settler::settle_transfer` with `TransferRecipient::OtherCompany` pointing at the lending bank.
3. Add a test: after a repayment turn, assert `sum(bank.reserves_increase) == sum(borrower.cash_decrease)`.

#### BLACK HOLE #3: Corporate Interest Payments Vanish (MONEY DESTROYED)

**Severity: HIGH — destroys interest payments every turn.**

In `corporate/manager.rs:272-280`:

```rust
let interest = if company.liabilities > 0.0 && ... {
    company.liabilities * (xibor + risk_margin)
} else { 0.0 };
company.liquid_capital = (company.liquid_capital - interest).max(0.0);
// ❌ interest is NOT credited to any bank!
```

The interest is subtracted from `company.liquid_capital` but never credited to any bank's income or reserves. It vanishes.

**Impact:** Money is destroyed equal to total corporate interest payments every turn. This partially offsets Black Hole #2 (money creation from phantom repayments), but the net effect is still massive capital drift because the two leaks are on different code paths and don't cancel.

**Fix:**
1. The `interest` payment should be routed to the lending bank via `transfer_settler::settle_transfer`.
2. This requires knowing which bank issued the loan — which requires the `Loan` struct to have a `borrower_id` (see Black Hole #2 fix) and the company to track which bank it owes.
3. Short-term: credit the interest to `country.budget.liquid_reserves` as a "central bank residual" so the money mass is preserved.

### 2.3 Product Black Holes — Inventory Caps

**Finding: Buildings DO have hard inventory caps. This is NOT a black hole.**

`Building.inventory_capacity` (entities/mod.rs:1019) is set during generation (corporate.rs:589, 998) and enforced in `execute_production_cycle` (b2b_orders.rs:859-940):

1. After production, if `total_inventory > inventory_capacity`, overflow is computed.
2. Overflow is routed to warehouses (commercial buildings with `storage_capacity`) — storage fees are charged.
3. If warehouse capacity is insufficient, remaining overflow **perishes** (destroyed with a financial write-down recorded in `inventory_write_down`).

**Minor issue:** The `inventory_capacity` default is `0.0` (`default_building_inventory_capacity()` at entities/mod.rs:1041). Buildings generated by the corporate generator get a proper capacity (`base_capacity * 10.0`, min 100.0). But buildings loaded from old saves or created by other paths may have `0.0` capacity, which would cause ALL production to overflow/perish immediately. A migration clamp is needed.

**Verdict:** Product black holes are NOT present. The inventory cap system is functional. The only risk is the `0.0` default for unmigrated buildings.

## PART 3: Incomplete Mechanics (One-Way Doors)

### 3.1 Corporate Downsizing

**Finding: Downsizing EXISTS but is shallow — no asset sales, no production halt, no demolition.**

The `CorporateAction::Restructure` variant (strategy.rs:57-63) is executed in `apply_action` (manager.rs:427-439):

```rust
CorporateAction::Restructure { layoffs, capital_write_off } => {
    if layoffs >= company.worker_capacity || capital_write_off >= company.fixed_capital {
        company.liabilities = (company.liabilities - company.fixed_capital).max(0.0);
        company.fixed_capital = 0.0;
        company.liquid_capital = 0.0;
        company.worker_capacity = 0;
    } else {
        company.worker_capacity = company.worker_capacity.saturating_sub(layoffs);
        if capital_write_off > 0.0 {
            company.fixed_capital = (company.fixed_capital - capital_write_off).max(0.0);
            company.liabilities = (company.liabilities - capital_write_off).max(0.0);
        }
    }
}
```

**What it DOES:**
- Reduces `worker_capacity` (lays off workers)
- Writes off `fixed_capital` (reduces book value)
- Reduces `liabilities` proportionally

**What it DOES NOT do:**
- Does NOT sell or demolish buildings (buildings remain with `owner_id` set, just `worker_capacity` reduced later in the turn at manager.rs:124-138)
- Does NOT halt production (buildings still produce in `execute_production_cycle` — just with fewer workers)
- Does NOT fire-sale inventory (goods remain in `building.inventory`)
- Does NOT cancel pending construction projects
- Does NOT notify the labor market that workers were laid off (no update to `ClassDemographics` unemployment)
- Does NOT route laid-off workers back to the labor pool

**One-way door:** Companies can expand (build, hire) but cannot meaningfully contract. The `Restructure` action reduces numbers on paper but leaves physical assets and production intact. A company with 0 `worker_capacity` still has buildings that produce (the production cycle uses `building.current_employment`, not `company.worker_capacity`).

**Refactoring Blueprint:**
1. When `Restructure` fires, also:
   - Route laid-off workers back to the regional labor pool (`ClassDemographics.population` / unemployment).
   - Mark buildings for capacity reduction (already done at manager.rs:124-138, but only if `worker_capacity == 0`).
   - Fire-sale excess inventory at discount prices (submit asks to the order book at 80% of market price).
   - Cancel pending construction projects (`building.active_project = None` with material recovery).
2. Add a `CorporateAction::Demolish { building_id }` variant for full asset liquidation.
3. Add a `CorporateAction::HaltProduction { building_id }` variant for temporary shutdown (sets `building.current_employment = 0` without firing).

### 3.2 Financial Markets — Loan Principal, Shares, Dividends

#### 3.2a Loan Principal Repayment

**Finding: Principal IS repaid on the bank's books, but the borrower never pays and `liabilities` never decreases.**

In `state/banking.rs:2013-2026`:
```rust
let payment = loan.principal / loan.term_turns as f64 + interest;
let actual_payment = payment.min(loan.outstanding_balance);
loan.outstanding_balance -= actual_payment;  // ✓ bank's loan asset decreases
```

**One-way doors:**
1. **Borrower never pays:** See Black Hole #2 — the borrower's `available_cash` is never debited.
2. **`company.liabilities` never decreases:** The `liabilities` field is incremented when a loan is taken (`manager.rs:409: company.liabilities += loan`) but is NEVER reduced by principal repayment. It's only reduced by `Restructure` (capital write-off). So the company pays interest on the FULL original loan amount forever, even as the bank's `outstanding_balance` decreases.
3. **Phantom `BankLoan` liabilities:** When `CorporateAction::Expand` uses `FinanceSource::BankLoan(loan)` (manager.rs:407-409), it does `company.liabilities += loan` but does NOT create a `Loan` record in any bank's `loans_issued` vec. So the company has a liability with no matching bank asset. The bank's loan repayment loop (banking.rs:2000) will never process this loan because it doesn't exist on any bank's balance sheet.

**Refactoring Blueprint:**
1. Add `borrower_id: String` to the `Loan` struct (state/banking.rs:144).
2. When `FinanceSource::BankLoan(amount)` is used, actually create a `Loan` record in the lending bank's `loans_issued` (requires finding a bank and calling the loan issuance function).
3. In the repayment loop (banking.rs:2000), after reducing `loan.outstanding_balance`, find the borrower by `loan.borrower_id` and debit its `available_cash` via `transfer_settler::settle_transfer`.
4. After repayment, also reduce the borrower's `company.liabilities` by the principal portion of the payment.
5. Add a test: after N turns of repayment, assert `company.liabilities == sum(remaining outstanding_balance across all loans of this company)`.

#### 3.2b Corporate Shares

**Finding: Shares are issued but ownership is not tracked in the corporate IPO path.**

The corporate manager's IPO path (manager.rs:455-491):
```rust
CorporateAction::Ipo { shares_to_float, reserve_price } => {
    // ... builds CorporateDecisionCtx ...
    if let Some(new_form) = try_apply_ipo(...) {
        let proceeds = shares_to_float as f64 * reserve_price;
        company.legal_form = new_form;
        company.liquid_capital += proceeds;      // ✓ company gets cash
        company.shares_count += shares_to_float;  // ✓ share count increases
        // ❌ company.owners is NOT populated!
        // ❌ shares are not listed on the stock exchange!
        // ❌ no buyer is debited — proceeds appear from nowhere!
    }
}
```

**One-way doors:**
1. `company.owners` is never populated — the `route_dividends` function (which iterates `company.owners`) would find no shareholders.
2. The `proceeds` (cash from share issuance) are added to `liquid_capital` but no buyer's cash is debited. The money appears from nowhere.
3. The shares are not listed on `country.stock_exchange` — they can't be traded.
4. The securities exchange has a proper `list_shares` / `process_ipo` path (exchange.rs) that DOES populate `owners` and list on the exchange — but it's never called from the corporate manager.

**Refactoring Blueprint:**
1. The corporate manager's IPO should call `SecuritiesExchange::list_shares` (or equivalent) instead of directly mutating `shares_count` and `liquid_capital`.
2. The IPO proceeds should come from actual buyers (funds, citizens, other companies) — debit their cash and credit the issuing company.
3. Populate `company.owners` with the initial shareholders.

#### 3.2c Dividends

**Finding: Dividends are paid but only reach monasteries. Citizen shareholders get nothing.**

In `apply_action` (manager.rs:441-453):
```rust
CorporateAction::PayDividend { total } => {
    company.liquid_capital = (company.liquid_capital - total).max(0.0);
    company.aggregated_stats.total_dividends += total;
    for cultural in &mut country.cultural_institutions {
        if let Some(&share) = cultural.owned_company_shares.get(&company.id) {
            let dividend_share = total * share;
            cultural.available_cash += dividend_share;  // ✓ monasteries get dividends
        }
    }
    // ❌ ClassDemographics shareholders get NOTHING
    // ❌ Fund shareholders get NOTHING
    // ❌ Treasury (state shares) gets NOTHING
    // ❌ The rest of 'total' vanishes!
}
```

**One-way doors:**
1. Only `cultural_institutions` (monasteries with `owned_company_shares`) receive dividends. All other shareholders (citizens via ClassDemographics, investment funds, the treasury for state-owned companies) receive nothing.
2. The dividend amount is debited from `liquid_capital` but only partially credited (to monasteries). The remainder vanishes — money is destroyed.
3. `company.aggregated_stats.total_dividends` is then OVERWRITTEN at manager.rs:146 with `total_profit.max(0.0)` — so the dividend stat doesn't even reflect actual dividends paid.
4. The proper `SecuritiesExchange::route_dividends` function (exchange.rs:648) exists and correctly routes to owners, brokerage accounts, and treasury — but it's **never called**.

**Refactoring Blueprint:**
1. Replace the monastery-only dividend routing with a call to `SecuritiesExchange::route_dividends`.
2. For state-owned companies (state_share > 0), route the state's portion to `country.budget.liquid_reserves`.
3. For citizen-owned shares (via funds), ensure the funds eventually distribute to `ClassDemographics.savings`.
4. Fix manager.rs:146 — `total_dividends` should accumulate, not be overwritten with `total_profit`.

### 3.3 Bankruptcy Cleanup

**Finding: The active bankruptcy path is a crude stub. The elaborate waterfall is dead code. Ghost references remain.**

#### Active Path: `CompanyLifecycle::liquidate_bankrupt_companies` (lifecycle.rs:62-128)

```rust
fn liquidate_bankrupt_companies(companies, buildings, _country, _year) {
    // Find companies with negative equity or 3+ consecutive loss years
    // (energy companies get strategic resolution instead)
    for idx in to_remove.into_iter().rev() {
        for building in buildings.iter_mut() {
            if building.owner_id == company.id {
                building.owner_id.clear();        // ✓ building orphaned
                building.current_employment = 0;   // ✓ workers fired
                building.worker_capacity = 0;      // ✓ capacity zeroed
                // ❌ building.inventory remains (orphaned goods)
                // ❌ building.active_project remains (orphaned construction)
                // ❌ building.fixed_assets remain (orphaned machinery)
            }
        }
        companies.remove(idx);  // ❌ company's cash vanishes
        // ❌ bank loans NOT repaid (liabilities vanish — bank loses asset)
        // ❌ bank.balance_sheet.loans_issued NOT cleaned (orphaned loans remain)
        // ❌ stock exchange NOT notified (orphaned listings remain)
        // ❌ frozen_company_cash NOT reclaimed (stays in justice_state)
        // ❌ B2B order book: OK (per-turn, no persistent orphaned bids)
        // ❌ shareholders get NOTHING (no liquidation distribution)
    }
}
```

#### Dead Path: `Syndic::execute_liquidation` (bankruptcy.rs:236-369)

This 130-line function properly:
- Seizes and converts FX balances
- Routes physical assets to `BankruptcyAuctionPool` with creditor claims
- Performs waterfall distribution (tax → bank loans → shareholders)
- Reclaims frozen cash from justice system
- Clears brokerage account

But it uses the **legacy `Bank` struct** (not `Company` with `BankBalanceSheet`), so even if wired in, it would need migration. And it's **never called**.

**One-way doors / ghost references from the active path:**
1. **Orphaned bank loans:** The company's `liabilities` vanish (company removed), but the bank's `balance_sheet.loans_issued` still contains the `Loan` record. The bank's `outstanding_balance` never goes to 0. The bank will continue accruing interest on a loan to a non-existent company. The repayment loop (banking.rs:2000) will reduce `outstanding_balance` but never mark it `Default` or `Repaid` for a removed borrower.
2. **Orphaned building inventory:** Goods in `building.inventory` remain after the company is removed. The building has no owner, so the goods sit forever (no one sells them, no one consumes them).
3. **Orphaned construction projects:** `building.active_project` remains. If a contractor was working on it, the project is stuck (no one to pay for completion).
4. **Orphaned stock listings:** If the company was listed on `country.stock_exchange`, its order book entries and share listings remain. Other investors could try to buy shares in a non-existent company.
5. **Shareholder losses:** Shareholders (citizens, funds, treasury) lose their entire investment with no liquidation distribution.
6. **Frozen cash not reclaimed:** `justice_state.frozen_company_cash[company.id]` remains forever (the dead `execute_liquidation` reclaims this at bankruptcy.rs:304, but the active path doesn't).
7. **B2B order book:** OK — the order book is rebuilt per turn, so orphaned bids are not persistent. This is the ONE area that's fine.

**Refactoring Blueprint:**
1. Migrate `Syndic::execute_liquidation` from legacy `Bank` to `Company` + `BankBalanceSheet`.
2. Wire `execute_liquidation` into `liquidate_bankrupt_companies` — call it BEFORE removing the company.
3. After liquidation, clean up ghost references:
   - Remove the company's `Loan` records from all banks' `loans_issued` (mark as `Default`).
   - Clear `building.inventory` (route to auction pool or destroy).
   - Cancel `building.active_project` (recover materials if possible).
   - Delist from `country.stock_exchange` (remove order book entries, mark shares worthless).
   - Reclaim `justice_state.frozen_company_cash[company.id]`.
4. Add a test: after bankruptcy, assert no bank has a `Loan` with `borrower_id == removed_company_id` and `status != Default`.
